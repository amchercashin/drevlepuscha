# Среда и перенос проекта

## Проверенная исходная среда

8 сентября 2026 года: MacBook Air M3, 8 ГБ общей памяти, macOS 26.6.2, Node.js 22.23.1, npm 10.9.8. На диске было свободно примерно 14 ГиБ; подкачка использовала около 3,7 ГиБ. Это снимок состояния, а не постоянный запас ресурсов.

Системный Node оставлен без изменений. Локально закреплены TypeScript 5.8.3, Babylon.js 9.25.0, Vite 8.2.2 и Playwright 1.63.0. Зависимости воспроизводятся из `package-lock.json`; каталог `node_modules` занимает около 163 МБ. Проверки используют уже установленный Chrome: отдельные браузеры и Blender не скачивались.

Node 22.23.1 соответствует опубликованному минимуму Vite 22.12+. Закреплённая версия сборщика запускается на этой среде. Источники: [Vite](https://vite.dev/guide/), [ветки Node.js](https://nodejs.org/en/about/previous-releases). Системное обновление Node для M0 сейчас не нужно; будущий переход выполнять одинаково на обеих платформах с обновлением pin-файла и повторными проверками.

## Первое открытие на macOS или Windows

1. Установить Node.js 22.23.1 для своей системы с [официальной страницы версии](https://nodejs.org/download/release/v22.23.1/). Для Git-переноса также нужен Git; для открытия ZIP он не обязателен.
2. Открыть терминал в корне проекта и проверить `node --version`.
3. Выполнить `npm ci`, затем `npm run doctor` и `npm run check`.

В PowerShell, если политика блокирует `npm.ps1`, использовать `npm.cmd ci`, `npm.cmd run doctor` и `npm.cmd run check`. Менять политику безопасности Windows для этого не требуется.

Команды работы с проектом используют Node и относительные пути. Для запуска и проверки не нужны Python, Homebrew, Unix-shell, пути `/Users/...` или папки Codex. `.node-version` фиксирует версию, но сам по себе не устанавливает её: без менеджера версий выполнить шаг 1 вручную.

## Перенос

Исходники, тесты, конфигурации и lockfile входят в общий GitHub-репозиторий. Приватные изображения исключены из публичной истории и остаются локально. После законченного проверенного изменения сохранять коммит и отправлять его на GitHub; push в main запускает публикацию Pages.

Два простых способа:

- Скопировать всю папку проекта, включая скрытую `.git`, но исключив `node_modules`, `dist` и временные результаты. Это переносит историю и незакоммиченные файлы. На целевой машине выполнить `npm ci` заново.
- Для передачи чистого состояния после коммита выполнить `git archive --format=zip --output=../drevlepuscha-source.zip HEAD`. ZIP содержит только закоммиченные файлы, без приватных референсов; история Git и незакоммиченные изменения в него не входят. Распаковать и выполнить `npm ci`.

`node_modules` нельзя переносить между macOS ARM и Windows: зависимости сборщика содержат платформенные компоненты. Одинаковые версии исходников и lockfile важнее одинакового содержимого этого каталога.

Архив первоначального комплекта находится отдельно в локальном архиве вне репозитория и не требуется для сборки. Его можно перенести дополнительно как исторический материал. Будущие `.blend`, исходные текстуры и `.glb` хранить в проекте с относительными связями; файл, оставшийся только в Downloads, не считается частью переносимой разработки.

Когда появятся сохранения игрока, браузерное хранилище само по себе не перенесётся с проектом. На M2 нужен экспорт/импорт JSON; текущий `save.example.json` является тестовым примером.

## Ограничения Mac

Перед новой крупной установкой выполнить `npm run doctor` и оценить размер загрузки, установки и временной распаковки. Проектный порог: если свободно меньше 10 ГиБ, остановить крупные установки и сначала согласовать освобождение места; личные файлы автоматически не удалять. Желательный запас перед большим импортом моделей — 20 ГиБ. Эти пороги — рабочая политика проекта, не системные требования двигателя.

Базовое разрешение воспроизводимых замеров — 1280×720, DPR 1. В обычном окне по умолчанию действует бюджет 3,7 Мп с сохранением пропорций и учётом Retina до 2×; качество выбирается в панели. Начальная сцена: один источник света и простой материал; тени и дальность подбирать измерениями. Один активный редактор и один браузерный сеанс; браузерные тесты сначала последовательно. Не добавлять Docker, виртуальную Windows, Unreal, Unity или большие наборы моделей без конкретной потребности.

Blender устанавливать при появлении задачи моделирования, предварительно сверив текущие системные требования и свободное место. Хранить `.blend` как исходник, `.glb` как экспорт для движка. Настройки единиц, осей, версия Blender и зависимости экспортёра должны быть записаны вместе с первым модельным файлом.

Сервер разработки слушает только localhost. WebGPU используется по умолчанию; при недоступности инициализации включается WebGL2. Режим можно выбрать в диагностической панели. Публикация выполняется через `.github/workflows/pages.yml` после проверок Linux и Windows.

## Что считать проверкой переносимости

Локальная проверка из отдельной папки подтверждает полноту исходников и независимость от исходного пути. Она не доказывает работу на Windows. Перед закрытием M2 выполнить на Windows `npm ci`, проверки, сборку и реальный проход в браузере, записав версию ОС и браузера, GPU, разрешение и FPS. Визуальные эталоны разных ОС сравнивать с учётом различий рендера; случайно появившуюся разницу не принимать автоматически.

## Запуск и воспроизведение M0

`npm run dev` открывает сервер разработки на порту 5173. Для стабильной сцены выполнить `npm run build` и `npm run preview` (порт 4173). Файлы `references/private` в сборку не входят.

`npm run test:browser` собирает приложение и выполняет проверки в установленном Chrome на обоих рендерах. Для Edge задать переменную среды `BROWSER_CHANNEL=msedge` средствами своей оболочки. Браузерная прогулка на Windows пока не проверена; установка, модульные тесты и сборка прошли на Windows runner в GitHub Actions.

При работающем preview выполнить `npm run qa:performance -- --renderer=webgl2`, затем `npm run qa:performance -- --renderer=webgpu`. Каждый замер: 30 секунд прогрева и три прохода по 60 секунд. Не переключать фокус окна браузера во время измерения: потеря фокуса ставит игру на паузу и делает замер недействительным.

`npm run qa:capture -- --renderer=webgpu` записывает шесть ракурсов и видео реального прохода в `qa/evidence`. Служебный API доступен только с параметром `?debug=1`. Итоги и границы проверки — в `qa/M0.md`.

Рабочая папка на этом Mac: `~/Developer/lotr`. Старый адрес в Documents — символическая ссылка для совместимости с уже открытым проектом. Переносить нужно содержимое настоящей папки, а не эту ссылку. Перемещение выполнено после обнаружения файлов `dataless` и многоминутных задержек чтения в Documents; глобальные настройки облачного хранения не менялись.

## Первая нагрузочная сцена M1

После сборки открыть `/?scene=m1`. Экспорт игрового дерева и автоматический кэш LOD воспроизводятся командой `node --experimental-strip-types tools/prepare-game-tree.mjs`; для ствола используется уже закреплённый Babylon; дальние кроны строятся из автоматически сгруппированных объёмов исходной листвы. Новых зависимостей нет. GLB содержит два материала и две общие текстуры 512 × 512. Геометрия кэша связана с хешем авторского исходника; модульный тест обнаруживает устаревание.

Основной режим разработки и измерений — WebGPU с LOD. Команда `node tools/performance-m1.mjs --renderer=webgpu` прогревает видимый Chrome при 1280 × 720 и выполняет один 60-секундный проход за прежней границей, от отметки 160 м. `--orbit-only` проверяет круговой осмотр там же. `--comparison` оставлен для явно нужного контрольного сравнения без LOD; по умолчанию он не запускается. WebGL2 остаётся резервом, отдельные регулярные замеры не требуются. Не повторять M0 после изменений только моделей; выбирать проверки изменённой части.

Во время замера не переключать фокус измерительного окна. Результат — `qa/evidence/m1-performance-webgpu.json`. Это предварительная проверка большого стенда, а не 30-минутная приёмка нагрева, сетевого стриминга и полного состава окружения.

## Meshy: референс → модель → лес

**Основной путь выбран Александром: А, концепт Codex → Meshy.** Б оставлен для сравнения. Первая проба от 8 сентября 2026 года: два пути из одного приватного рисунка. А — концепт встроенного `imagegen` Codex; Б — Meshy Image-to-Image, `nano-banana-2`. Один и тот же промпт, разные генераторы; это одна пара примеров, а не статистический тест качества сервисов. Концепты имеют разные размеры кадра: 1024 × 1536 и 896 × 1200. [Конфигурация и полный промпт](../config/meshy-tree-trial.json), исходные и нормализованные GLB, концепты и квитанции — в `assets/trees/meshy-a` и `meshy-b`.

### Выбор настроек

| Решение | Причина и ограничение |
|---|---|
| Smart Topology T2, `target_polycount: 5000` | Прямая генерация игровой сетки; доступный диапазон 100–15 000. Итоговое число приблизительное: в пробе 5318 и 5470 треугольников. |
| Один отдельный объект на белом фоне | Полные корни и крона, один ракурс ¾, нейтральный свет, видимые связи ветвей. Речной пейзаж служит источником стиля, затем из него создаётся референс одного дерева. |
| `texture_resolution: 2k`, `enable_pbr: false` | Для первого стилизованного образца достаточно base color; в игре матовый материал. 4K/8K и дополнительные карты сейчас не оправданы. |
| GLB, `auto_size: false` | Текстура внутри файла; метрический масштаб и начало координат задаются локально при подготовке, высота этой пробы — 18 м. |
| Без `topology`, `should_remesh`, `decimation_mode` | T2 не требует remesh; адаптивный режим имеет приоритет над желаемым числом граней. Не передавать неподдерживаемые T2 `image_enhancement` и `remove_lighting`. |

Параметры проверены в [Image to 3D API](https://docs.meshy.ai/en/api/image-to-3d). API не даёт жёсткой гарантии точного цвета: палитру и художественный язык задают изображение и, при необходимости, отдельное ретекстурирование. У этой пары текстура строилась по каждому концепту без дополнительного текстового переопределения, чтобы не смешивать условия сравнения.

**Несколько ракурсов:** [Multi-Image API](https://docs.meshy.ai/en/api/multi-image-to-3d) принимает 1–4 изображения одного объекта; это путь Standard, не Smart Topology. Его стоит пробовать, если один ракурс даёт плохую обратную сторону. Согласованные фронт/бок/тыл полезнее нескольких противоречащих друг другу рисунков. Не подавать коллаж нескольких деревьев как один вход Smart Topology. Для Standard после получения подробного исходника нужен отдельный remesh до игрового бюджета; этот путь пока не тестировался.

**Концепт внутри Meshy:** [Image-to-Image](https://docs.meshy.ai/en/api/image-to-image) работает с 1–5 исходными изображениями и имеет режимы нескольких видов и удаления фона. В нашей пробе использованы одна картинка, один выход, обычный белый фон и портрет 3:4. По [справке веб-сервиса](https://help.meshy.ai/en/articles/13696156-how-to-use-the-text-to-image-feature) Text to Image недоступен на Free. По [тарифам API](https://docs.meshy.ai/en/api/pricing) такой концепт стоит 6 кредитов, T2 с 2K-текстурой — 15. Фактически списано 36 кредитов за два дерева и один концепт. Покупка подписки или кредитов скриптами не выполняется; доступ и остаток проверяются через API.

### Подключение и команды

Официальный [MCP Meshy](https://docs.meshy.ai/en/api/ai) закреплён на `0.5.1` в отдельном `tools/meshy/package-lock.json`. Он не входит в зависимости браузерной игры. На Mac зарегистрирован в Codex как `meshy`; локальный STDIO-сеанс вернул 24 инструмента и действительный баланс. Новый набор инструментов может потребовать нового сеанса Codex. Платные задачи этой пробы выполнялись через REST-скрипт ниже: официальный MCP-клиент автоматически повторяет POST при некоторых сетевых ошибках, а наш скрипт сохраняет намерение до отправки и запрещает повторную оплату той же задачи.

1. Создать `.env.meshy.local` с `MESHY_API_KEY=...`. Файл исключён из Git и запрещён сервером Vite. В код, браузер и публичные JSON ключ не включается.
2. Для MCP: `npm ci --prefix tools/meshy`, затем `node tools/meshy/setup.mjs`. Нужен установленный Codex CLI. Команда делает приватную копию конфигурации и регистрирует путь этого checkout; после переноса её нужно повторить. Секреты между машинами через Git не переносятся.
3. Проверить доступ: `node tools/meshy.mjs balance`.
4. Создать концепт Б: `node tools/meshy.mjs concept`; затем `node tools/meshy.mjs status concept` и после `SUCCEEDED` — `node tools/meshy.mjs download concept`.
5. Создать модель: `node tools/meshy.mjs model a` (или `b`), затем `status a` и `download a` с тем же префиксом команды.
6. После `npm ci --prefix tools/meshy` подготовить игровую модель и LOD: `node --experimental-strip-types tools/prepare-meshy-tree.mjs a`, аналогично для `b`.

Эта пара уже выполнена: повторный `model a` останавливается до обращения к платному API. Прерванную работу продолжать через `status`/`download`; при неизвестном результате POST сначала сверить ID задачи в Meshy. Локальные задачи и полные ответы хранятся в `references/private/meshy-runs/<id>`. Подписанные ссылки не публикуются. Модели скачиваются сразу: [документация хранения API](https://docs.meshy.ai/en/api/asset-retention) предупреждает об удалении через три дня у обычных API-клиентов.

Для следующего ассета скопировать конфигурацию, задать новые `id`, `reference`, `outputs` и промпт; передавать путь конфигурации третьим аргументом, например `node tools/meshy.mjs concept b config/new-asset.json`. Создать и сохранить концепт А встроенным генератором в `outputs.a/concept.png`. Не менять ID уже оплаченной задачи ради повторной отправки в те же выходные файлы. Подключение выбранной модели к сцене остаётся явным в `src/runtime/tree-assets.ts`.

### Импорт, вариации и приёмка

Импорт принимает статический GLB с треугольниками, UV0 и встроенными PNG/JPEG; неподдерживаемые сжатие, скелет, morph targets или обязательные расширения дают ошибку. Применяются узловые преобразования, основание центрируется по нижним корням, высота переводится в метры. Ближняя текстура сохраняется без перерисовки. Вход проверяется по числу материалов, треугольников и размеру текстуры.

**Исправление LOD:** обычный QEM нарушал атлас и давал зелёные стволы. В локальном `meshy-lod.mjs` JPEG декодируется `jpeg-js 0.4.4`, серо-лиловая кора отделяется от зелёной листвы по цвету, цвета переносятся на вершины. `meshoptimizer 1.2.0` упрощает эти части с учётом цвета. У LOD 2 листва заменяется замкнутыми объёмами, сохраняющими расположение групп крон. Затем части объединяются: на экземпляр остаётся один материал и одна сетка. LOD 1/2 обходятся без атласа; исходный LOD 0 не изменяется. Результат А: **5318 / 1413 / 224** треугольника; Б: **5470 / 1428 / 211**. Расчёт выполняется при подготовке, новые библиотеки не входят в игру. Алгоритм разделения рассчитан на эту палитру дерева и JPEG; для другого типа объекта, иной палитры или PNG нужен другой профиль подготовки. Не применять его к камням вслепую.

**Вариации одной модели:** `runtime.placement` в конфигурации задаёт высоту 0,60–1,00 (10,8–18 м до заглубления), ширину 0,45–0,78, глубину относительно ширины 0,82–1,18, поворот 0–360° и наклон до ±2° по каждой горизонтальной оси. Четыре контрольных дерева сохраняют специально заданные пропорции с уменьшением. Позиции и ID прежние, вариации воспроизводимы. Корни погружаются на 0,85 м × высоту экземпляра плюс запас на наклон и перепад рельефа. Это настройки размещения общей геометрии, без отдельной сетки для каждой копии. Преобразования совпадают в ближней отрисовке и дальних группах; столкновения учитывают ширину, глубину и небольшой наклон.

Цвет А рассчитывается отдельно от размещения: `src/domain/tree-tone.ts`, версия `tree-tone-v1`, плавная интерполяция рощиц 48 м плюс случайность по ID. Вектор из трёх чисел передаётся обычным и дальним экземплярам через общий атрибут; прозрачные копии используют тот же вектор через uniform. `TreeTone` меняет albedo до освещения, с меньшей силой на серой коре; зелёная листва определяется по исходному цвету. Новых текстур, индивидуальных материалов или сеток нет. Переключатель «Разные оттенки деревьев» меняет силу эффекта, не перестраивая лес. Целевая проверка: `npx playwright test tests/browser/tree-tone.spec.mjs --project=webgpu`; полный повтор сравнения А/Б для этого изменения не нужен.

Meshy выдал один меш и атлас, без редактируемых параметров ветвей. Расположение самих развилок у копий одинаковое; ветер и структурные вариации ветвей не реализованы. Столкновения приближают ствол; ходьбы по поверхности крупных корней и деформации под грунт нет. Посадка проверена на кадрах и центральном маршруте, но не означает ручной проверки каждого из 4967 деревьев.

Открыть `tree.html?model=meshy-a` / `meshy-b`: доступны концепт, одинаковые ракурсы, сетка, LOD и скачивание GLB. **Обычный M1 теперь использует А**; `?scene=m1&tree=meshy-b` — сравнение, `?scene=m1&tree=game` — прежнее авторское дерево. Для обеих проб применяется одинаковый профиль размещения. Форму и цвет оценивать после прогулки, а не по превью сервиса. Дальние кроны приблизительны; геометрические пересечения соседей не устраняются автоматически.

Проверки: `npm run check`, `npm run build`, `npx playwright test tests/browser/meshy.spec.mjs tests/browser/tree.spec.mjs tests/browser/forest.spec.mjs --project=webgpu`. Для повторного замера выбранного А при работающем preview — `node tools/qa-meshy.mjs`; `--compare` нужен только для явного повторного сравнения двух путей; [результаты](../qa/evidence/meshy/performance.json). Сохранённые [проверки GLB](../qa/evidence/meshy/gltf-validation.json) относятся к исходным и нормализованным моделям, а также обоим экспортируемым LOD этой пары: ошибок и предупреждений нет.

## Процедурные варианты ассетов леса

Рабочий путь: **концепт → один Meshy GLB → локальные варианты формы → LOD → кэш → размещение копий**. Оплачивается только новый исходный GLB. `npm run assets:prepare` не обращается к Meshy и не запускается во время игры. Список исходников — `config/forest-asset-library.json`; параметры каждого — `config/meshy-*.json`. Для подготовки нужна существующая отдельная среда `npm ci --prefix tools/meshy`; новых зависимостей не добавлено.

```text
npm run assets:prepare
node --experimental-strip-types tools/prepare-forest-asset.mjs config/meshy-fork-oak.json
npm run check
npm run build
```

Первая команда перестраивает библиотеку целиком; вторая — только изменённый профиль и обычно достаточна. В `runtime.variantParameters` можно задать параметры каждого варианта: `bendX`/`bendZ` — смещение верха в долях исходной высоты, `twist` — поворот верха в радианах, `spread` — ширина верхней части, `crownHeight` — её высота. У предметов также работают `stretchX`/`stretchZ`. Без явных параметров они воспроизводимо вычисляются из стабильного ID и номера варианта. Вариант 0 по умолчанию сохраняет исходную форму. Количество ограничено 1–4: готовые формы многократно используются, а не создают отдельную геометрию для каждого дерева. Значения проверяются; чрезмерный изгиб/скручивание или нечисловые параметры останавливают подготовку.

У дерева нижние `min(6 м, 60% высоты)` остаются неподвижны; верх меняется непрерывно, без разрезания ветвей. Соединённые точки преобразуются одинаково, UV сохраняются, нормали пересчитываются. Это изменение существующего объёма, **не генерация новых развилок и не редактируемый скелет ветвей**. Для иной топологии нужна другая исходная модель. У предметов основание сохраняет высоту, горизонтальный pivot центрируется; отдельные корни к конкретному склону не деформируются. Посадка использует высоту под преобразованной опорной областью.

У предметов `runtime.tintRGBByVariant` при необходимости задаёт три множителя цвета (0,8–1,2); иначе применяются сдержанные холодный и тёплый варианты. Это цвет поверхности, не рост нового мха. Цвет деревьев дополнительно меняет существующий `TreeTone` по ID и положению рощи. Все формы одного исходника используют одну текстуру и общие материалы.

Результат каждого профиля — `variants.json` рядом с `source.glb`: параметры, source/profile hash, версия алгоритма, границы, число треугольников и геометрия. Для дерева автоматически вычисляются три LOD; малые предметы на 496–770 треугольников пока имеют один уровень и стоят ограниченным набором у маршрута. При массовом размещении предметов сначала добавить дистанционный отбор/LOD и замер; текущий набор не означает неограниченное размножение.

Деревья выбираются детерминированно: в основном лесу один вариант на рощу 64 × 64 м, вдоль пробной тропы — смешанный состав. Позиции и количество сохраняются, посадка и коллайдер берутся от выбранной формы. Дальний батч использует тот же вариант и преобразование, что ближний LOD. `?scene=m1&variety=0` оставляет одно основное семейство для изолированной диагностики; обычный M1 включает библиотеку. Старые проверки А/Б используют `variety=0`, не запускают сравнение отвергнутого Б без конкретной причины.

Проверки: `tests/asset-variation.test.mjs` — стабильный seed, сохранение основания и порядка высот; `tests/tree-family.test.mjs` — фиксированное число деревьев и ограничение дальних групп; `qa/evidence/asset-pipeline.json` — байтово одинаковая повторная сборка одного реального исходника. Для сцены `node tools/check-forest-variety.mjs --renderer=webgpu` / `webgl2` при preview на 4176; проверяются состав, камера и полнота передачи ближнего/дальнего леса. Фотографии пользователя и подписанные Meshy URLs остаются приватными.

## Производительность новых элементов

Оптимизация входит в производство элемента, а не откладывается до наполнения леса. Сначала сохранять видимые формы, цветовые массы, глубину и управление; тени должны создавать мягкую атмосферу, точность каждой ветки не является самостоятельной целью (решение Александра, 9 сентября 2026).

- Геометрию, LOD и вариации готовить офлайн. Во время движения не выполнять синхронное объединение больших мешей и генерацию нескольких тяжёлых ячеек в одном кадре. Заранее готовить ограниченную область, переиспользовать буферы; проверять, что подгрузка успевает при 15 м/с и развороте.
- Повторяющиеся объекты используют общие геометрию/материалы и пространственные пакеты. Число видов не должно автоматически умножать вызовы отрисовки всех дальних ячеек. Оценивать draw calls и стоимость пикселей вместе с треугольниками.
- Разделять данные мира и активную область: близкие коллизии выбираются пространственным запросом, затем проверяются точным прежним алгоритмом. Точность видимости героя не заменять грубым bounding box.
- Тени используют отдельные общие экземпляры подходящего LOD. Не пересоздавать геометрию при смене ячейки. Не отбрасывать caster только потому, что он за камерой. Художественное дальнее затенение не должно зависеть от строки конкретного фильтра PCF.
- У каждого post-process должен быть потребитель результата. Размер input target и размер output pass проверять отдельно: цвет/глубина сцены остаются чёткими, мягкое рассеяние можно считать в меньшем разрешении. Не суммировать асинхронные медианы GPU-счётчиков как бюджет кадра.
- Обычный непрозрачный объект не должен получать дорогое поведение переходного объекта: dither/discard и отдельные fade-копии нужны только там, где они работают. Для alpha-tested листвы отдельно проверять overdraw и мерцание, не принимать уменьшение полигонов за доказательство ускорения.
- До/после сравнивать одну версию содержимого, одинаковые разрешение, MSAA, камеру и маршрут. Снимать картинки вне измерительного интервала, GPU-прогоны других задач выполнять последовательно. Проверять контуры, кроны снизу, тени, LOD и прозрачность в движении; числовая разница пикселей дополняет, но не заменяет просмотр.
- Различать CPU-время обработки, интервал кадров и GPU-время. При упоре в частоту экрана не обещать рост FPS. Проверять P95/P99 и пики границ ячеек, а не только среднее. Тепловую и платформенную приёмку отмечать отдельно.
- После реализации выполнять `npm run check` и только проверки изменённого поведения. Новую библиотеку, temporal reconstruction, глобальный стриминг или сложный диспетчер вводить только при измеренной необходимости.
