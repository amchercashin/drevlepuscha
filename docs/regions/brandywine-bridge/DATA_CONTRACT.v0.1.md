# Контракт данных и границы готового пакета

## 1. Источники истины

`source/design_v0_1.md` — неизменённая исходная спецификация. Единицы её таблицы координат — километры.

`data/region-source.v0.1.json` — машиночитаемая конкретизация для первого макета. Здесь **все горизонтальные координаты — метры**. Это не формат текущего `geography.json` Древлепущи и не обещание, что текущий `WorldData` уже умеет его загружать. Для подключения требуется описанный в плане адаптер.

Сюда входят 17 POI, оси рек с уровнями/ширинами/глубинами, 3 дороги, изгородь с проёмом, 3 полигона лесного покрова, 6 форм рельефа, граф из 31 узла/40 связей, 6 объектов перехода и профили путников.

`topology-derived.json`, SVG, HTML, preview raster и validation report производны. Исправления делаются в source JSON и генераторе, затем `node tools/build-resources.mjs`. Не редактировать независимо картинки и исходную географию.

Канонический статус POI означает только, что место существует в выбранном дизайне по литературным опорам. Координаты, размеры и высоты в пакете авторские. Прежняя литературная проверка не заменяется этим техническим аудитом.

## 2. Координаты и границы

- Local EN: origin — середина Брендивинского моста; E направлен на восток, N на север.
- Точка `(0,0)` — середина моста, а не spawn. Высота поверхности Брендивина под мостом принята за 0 м местной вертикальной системы.
- Babylon RH: `x=e-origin.e`, `z=origin.n-n`, `y=h`. Ось N нельзя перепутать с положительной Z.
- Граница игры: E `[−1600,2400]`, N `[−1500,2500]` = ровно 16 км².
- Покрывающая граница хранилища при плитке 512 м: E `[−2048,2560]`, N `[−1536,2560]` = 72 плитки. Пояс за игровой границей — данные/продолжение вида, не дополнительные игровые задания.
- `atlasRegistration` не заполнен. До проверки большого файла географии регион запускается автономно. Недопустима автоматическая подгонка масштаба или перенесение Старого леса к мосту.

Предварительные якоря исходного дизайна сохранены. Развилка дороги к Стоку спроецирована на ось Восточной дороги: вместо `(−380,−60)` используется `(−380,−76)` м. Эта локальная техническая поправка явно записана в JSON.

## 3. Гидрология и высота

`river.stations` содержит `[e,n,levelM,widthM,depthM]`, по направлению вниз по течению. Ширина/уровень/глубина интерполируются между станциями. The Water заканчивается ровно на оси Брендивина; нормальный уровень обоих в устье = 0,31 м. У притока нет устьевого водопада.

Широкая речная полоса на SVG — отображение станций, не готовый береговой mesh. В производственном построении нужна согласованная сглаженная геометрия: берега, визуальная вода, wetness и глубина выводятся из одного sampler. Не рисовать один spline, а коллизии считать по другому.

`terrain-preview.f32le`: 251 × 251 значения Float32 Little Endian, шаг 16 м, южная строка первой, E меняется быстрее N. Всего 252 004 байта. Origin `[-1600,-1500]`, концевые узлы включены. Метаданные и SHA-256 рядом. Метрический масштаб по высоте сохраняется, вертикальное преувеличение не задано.

**Preview raster не содержит мостовых настилов, окончательно выровненных дорог, фундаментов и детальной береговой линии.** Он пригоден для вида сверху/обсуждения общих форм. Нельзя назначить его окончательной коллизией и объявить мост готовым.

Для production сначала единый 2-метровый базовый sampler; варианты более редких удалённых плиток — после проверки швов. Детали 0,25 м только локально, с нулевым смещением в зоне перехода/шва, аналогично подходу showcase. Мост — отдельная поверхность поверх глубокого дна.

## 4. Граф и переходы

Узел — удобная стратегическая точка. Ребро — кандидат маршрута с фактической полилинией и длиной. Граф **не заменяет навигацию в свободном пространстве** и не делает остальные поля непроходимыми.

`edge.kind`: road/path/bridge/boat/ford/gate. `profiles` определяет, кто подходит по размеру и способу движения. `crossingId` связывает маршрут с объектом перехода. Пересечение линий на картинке не создаёт нового узла: связь определяется только ID в данных.

В первой версии всего шесть переходов: главный мост, мостик притока, сезонный брод притока, Северные ворота, нижняя лодка, верхняя лодка. В Брендивине нет второго пешеходного брода.

`findRoute` из `tools/region-core.mjs` использует Dijkstra по состоянию `(node, lowerBoatSide, upperBoatSide)`. Если лодка стоит на другом берегу, ребро сейчас недоступно. Переправа меняет сторону лодки, и это влияет на оставшуюся часть того же маршрута. `initialSide=0` означает первый endpoint, `1` — второй, `-1` — лодка отсутствует. Время посадки включается один раз на пересечение по текущей упрощённой модели.

HTML-просмотрщик при каждом новом расчёте сбрасывает состояние к исходному — это намеренно не сохранённая игра. Node API принимает `boatSides`, поэтому можно продолжить обратный маршрут с `finalBoatSides` предыдущего расчёта.

Сухопутное время сейчас равно длине / заданной скорости, без уклона, грязи, разговоров и остановок. Это нижняя ориентировочная оценка, не гарантия длительности задания. Повозка пока только профиль доступности; её управление в движке не реализовано.

## 5. Предлагаемые runtime-интерфейсы

Ниже контракт проектирования, а не уже имеющиеся API репозитория. Конкретное размещение файлов агент уточняет после diff.

```ts
type EN = { e: number; n: number };
type WaterState = 'low' | 'normal' | 'high';
type MovementMode = 'walk' | 'boat';

interface RegionDefinition {
  id: string;
  contentVersion: string;
  seed: number;
  geographyKind: 'old-forest' | 'brandywine';
  dataBaseUrl: string;
  assetBaseUrl: string;
  cacheNamespace: string;
  playBounds: { minE: number; maxE: number; minN: number; maxN: number };
  spawn: EN;                 // сухая точка у двора, не центр реки
  spawnSupportId?: string;
  cameraProfile: 'showcase';
}

interface SurfaceQuery {
  terrainHeight(e: number, n: number): number;
  waterAt(e: number, n: number, state: WaterState):
    { levelM: number; depthM: number; bodyId: string } | null;
  supportAt(p: EN, context: {
    currentHeightM: number;
    currentSupportId?: string;
    movementMode: MovementMode;
    maxStepM: number;
  }): { heightM: number; supportId: string; material: string } | null;
  blockedSegment(a: EN, b: EN, heightM: number, radiusM: number): boolean;
  readyAt(p: EN): boolean;
}

interface CrossingState {
  id: string;
  revision: number;
  open: boolean;
  boat?: {
    entityId: string;
    position: EN;
    dockId?: string;
    occupiedBy?: string;
  };
}
```

Не возвращать `max(terrainHeight, bridgeHeight)` без контекста: персонаж/лодка под мостом не должен телепортироваться на настил. Проходимость вдоль подхода выбирает достижимую опору, а не самую высокую. Первую реализацию можно ограничить ходьбой сверху и лодкой в отдельном режиме; ограничение должно быть явным.

Загрузка визуальной плитки и существование объекта перехода — разные вещи. Выгрузка mesh не удаляет лодку из состояния и не создаёт её заново. Аналогично рендерный LOD не меняет форму коллизии.

## 6. Сохранения и будущая сеть

Сохранять минимум: `saveVersion`, `regionId`, `contentVersion`, seed, player pose/support, water preset, crossings с устойчивыми ID, состояние активной встречи. Не сохранять ссылки на Babylon meshes, экземпляры materials и номер рендерной плитки как смысловой ID.

Существующая многопользовательская сцена не считается автоматически совместимой с новым регионом. До её подключения нужен handshake regionId/contentVersion и авторитет для перемещения лодок/встреч. Для первого пространственного прототипа — одиночный режим. Локальный `CrossingState` всё равно не должен зависеть от UI/LOD, чтобы эту границу не переписывать позже.
